# Перенос Audio Transcriptions на новую версию NagramXF

Функция сохранена отдельным коммитом `66ca09942`. Ветка `feature/audio-transcriptions` содержит этот коммит и отдельный коммит инструментов переноса и сборки. Ветка `asr-apk-arm64-20261102` содержит только прежний APK.

## Перенос

В чистом checkout репозитория:

```sh
git fetch origin
git switch feature/audio-transcriptions
bash Tools/asr/port-update.sh dev asr/13.2.0
```

Замените `13.2.0` на новое имя. Вместо `dev` можно указать upstream-тег или SHA, доступный в origin. Скрипт получает актуальную базу, создаёт новую ветку и переносит коммиты функции и инструментов. Он не делает reset, не создаёт worktree, не отправляет изменения и не исправляет конфликты автоматически.

При конфликте проверьте `git status`, исправьте файлы и выполните `git cherry-pick --continue`. Отмена: `git cherry-pick --abort` (созданная ветка останется). Если upstream уже содержит функцию, сначала сравните реализацию; не используйте `--skip` вслепую.

После переноса:

```sh
git submodule update --init --recursive
bash Tools/asr/check-protocol.sh
git diff dev...HEAD
# После проверки изменений:
git push -u origin asr/13.2.0
```

Push ветки `asr/**` запускает workflow **ASR ARM64 APK**. Откройте завершённый запуск GitHub Actions → Artifacts → `NagramXF-ASR-arm64-...`, скачайте ZIP и извлеките APK. Для скачивания нужна авторизация GitHub; срок хранения — 30 дней. Workflow не публикует релизы и не отправляет сообщения.

Ручной `workflow_dispatch` предусмотрен, но кнопка появляется после включения workflow в default-ветку (`dev`). Пока workflow только в feature-ветке, используйте push `asr/...`. PR можно принять отдельно; автоматического слияния нет.

## Однократная настройка подписи

Для обновления поверх установленной тестовой сборки нужен тот же приватный ключ подписи. Новый ключ для каждого запуска создавать нельзя. Сделайте закрытую резервную копию существующего ключа; не коммитьте его и не отправляйте в чат.

Текущий ключ остаётся только в облачной среде: `/workspace/apk-signing/development.jks`. Его параметры должны передаваться приватно, а не записываться в репозиторий. SHA-256 сертификата проверенного APK (это публичный отпечаток, не приватный ключ):

```text
7acf3ef0a09d5c655daf9a7cf3988d2567fb8090471e8f29b5e990f86b5ea5b4
```

В Settings → Secrets and variables → Actions репозитория нужны четыре секрета:

| Имя | Значение |
| --- | --- |
| ASR_KEYSTORE_BASE64 | Base64 содержимого существующего keystore |
| ASR_STORE_PASSWORD | Пароль хранилища |
| ASR_KEY_ALIAS | Alias ключа |
| ASR_KEY_PASSWORD | Пароль ключа |

Запись секретов в этой сессии не выполнена. Нужны явное разрешение владельца на передачу приватного ключа в GitHub Secrets и доступ к Actions secrets (чтение их списка текущей интеграцией вернуло HTTP 403). Не присылайте токены или ключи в чат.

Без секретов workflow останавливается с понятной ошибкой, не создавая случайную новую подпись. Android также требует, чтобы versionCode следующего APK не был ниже установленного (у проверенной сборки — 1252).

## Проверки

`bash Tools/asr/check-protocol.sh` запускает 28 проверок URL, multipart, MIME, сохранения байтов и разбора ответа. Нужны JDK 21, curl и доступ к Maven Central. Версии зависимостей теста соответствуют текущему проекту; обновляйте их при обновлении зависимостей upstream.

Workflow собирает `TMessagesProj:assembleNormalStaging` для ARM64, проверяет подпись, выравнивание 16 КБ и архитектуру, сохраняет APK и SHA-256. SDK 36, NDK 27.2.12479018 и CMake 3.31.6 соответствуют текущей базе. При изменении требований upstream обновите workflow согласно его CI.

Перенос коммитов не гарантирует совместимости с любыми будущими изменениями. Дождитесь успешной сборки и проверьте оба режима на устройстве. Полная ARM64-сборка текущей функции уже прошла, пользователь подтвердил распознавание. Новая GitHub Actions-сборка пока не проверена: сначала необходима настройка подписи.
